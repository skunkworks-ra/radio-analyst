The three tiers

T1 Loop, no model

A fixed sequence of tool calls, or arithmetic over tool outputs. The loop runs it and puts the results in the brief. Every before/after check in stages.json is T1.

T2 Small model

A parameter set by a skill rule from named measured values: a lookup table, a ranking with a stated tie-break, a fixed call template. A skill table answers the question.

T3 Opus

A trade-off that needs the science goal, an anomaly, a recovery, or a review of a result against outside knowledge. Also any T2 step whose posterior check comes back anomalous.

The rule that keeps this honest. The brief is built from ground truth with no model in the path. A small model may act beside Opus; it never summarises data for Opus to decide on. A mis-summary turns into a confident wrong decision and leaves nothing on disk to show it.

Where this fits the driver

On driver-v2 the model decides and the loop executes, and they never run at the same time (PLAN.md, "The turn"). Two of its rules shape where the tiers can live:

  • The driver holds no tool list and no stage→tool table. The "leash" was dropped on purpose, because a stage table would refuse legitimate recovery (07b).
  • The driver may report a number but never name a verdict. No threshold file; the thresholds live in the skills.

So tier routing has to be skill-owned data that the driver reads, never driver code. The natural home is .claude/skills/reduce/stages.json: give each step a tier and an escalate_when naming the check that sends it to T3. The driver reads both fields the same way it reads the labels from ms_workflow_status, and holds no copy of them. The T1 checks follow the same pattern: the loop runs whatever before/after the contract names, and knows no tool names of its own.

scope-split carries the analyst-side groundwork: the versioned stage_log, ms_workflow_status reading state from the stage log, and archiving a caltable on retry instead of deleting it. The tier fields depend on that, and the driver itself moves to a separate harness repository.

Open for Krishna: does a tier field in stages.json count as the stage table the plan rejected? I'd argue it doesn't: it selects a model, never refuses a decision, and an escalation only raises the tier.

  10. mediumfixedRadiometer estimate: polarisations and efficiency

    Fixed, by expert ruling: the VLA OSS "Sensitivity" equation 1. σ = SEFD / (ηc √(npol N(N−1) tint Δν)) × w. ηc 0.93 (8-bit) or 0.78–0.83 (3-bit); npol 2 for Stokes I/Q/U/V; w ≈ 1.2 for robust weighting, which the template uses; for a mosaic, tint is the time on one pointing. The old form was about 1.3× the true noise, so the "> 2×" check fired at about 2.6×. VLA SEFDs now from OSS Table 3.2.1 (P 2790, X 250; Ku–Q added).

Reasons: the cause stays in the data for every later solve, and applycal's default applymode='calflag' discards the matching target data anyway, with nothing in the MS flag versions to say why. ms_flag_caltable(mode='manual') exists as the last resort, on any table type including K; flagdata does not support single-polarisation manual flags on a caltable. Both tools refuse an empty selection: an integration test shows flagdata(mode='manual') with no selection flags 100% of a real gain table.

    With fewer than 10 solution intervals, ms_flag_caltable refuses, and the skill says to flag "by hand" from ms_calsol_stats outliers. No step or tool says how. On 3C391, with one or two scans per calibrator, this is the normal case.

How Haiku reads these docs

Method. Haiku was given a snapshot of the skills at b590e74 (before the A1/A2 edits) and a 3C391 scenario: the fields, refant ranking, flag fractions, PA spreads and run scope. It was asked to walk the reduction on paper: the exact call for each step, the line it followed, and every point where it was unsure. It called no tools.

Two things weaken the result. The prompt named the areas to watch: the final applycal calls, the selfcal calls, the D-term source and the gridder. Those are where A1–A3 and A12 sit, so Haiku catching them is not independent evidence. It also read the live repo copies to compare, so it had seen the A1/A2 fixes. It did notice by itself that the snapshot's polcal apply contradicts 07 Step 7. Its value is in what it found outside the named areas: A25–A30.

BehaviourExampleWhat it means for the tiers

Paper and live runs differ. On paper, told to be careful and to list doubts, Haiku was cautious and literal. In the April live run it explained away an RMS 9.5× the radiometer estimate. The live failure was in reviewing a result, not in following a template. That supports T2 for template steps and T3 for every review of a measured outcome.
